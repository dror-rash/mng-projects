# ADR-0013: Where secrets and owner-only config live, and how a new workspace gets them

- **Status:** accepted (owner, 2026-11-14)
- **Date:** 2026-11-14

## Context
The owner works from several machines and cloud terminals (another Mac, Codespaces, Cloud Shell, Windows through WSL2, claude.ai/code),
and more people may join later. Today the owner-only config exists on one Mac only, git-ignored:
`infra/terraform.tfvars` (project, region, repository, alert email, billing account, budget and its currency) and
`infra/backend.hcl` (state bucket and prefix). Neither holds a credential: the project id is already public in
`docs/PLAN.md`; the alert email (personal data) and the billing account id are private but not secrets.

The real secrets (database passwords, Better Auth secrets) are generated by Terraform into Secret Manager and also sit
in the Terraform state, in the hand-made, versioned state bucket `gs://<project>-tfstate`. Local development shares no
secret: `.env` holds Docker defaults and a `BETTER_AUTH_SECRET` any random value satisfies. The CI-only demo login
(`DEMO_EMAIL`) is a GitHub repository secret.

Constraints: the repository is public (CLAUDE.md rule 7: no secrets in the repo, production secrets in Secret
Manager); GCP changes go through Terraform (rule 10); the project targets about US$15 a month, and its six active
Secret Manager versions already use the free tier (a seventh costs about US$0.06 a month).

## Decision
Every value has one home, by class. The owner's rule: **non-secret config lives in the state bucket; any real secret
lives in Secret Manager, never in the bucket.**
1. **Production secrets:** generated by Terraform into Secret Manager, read only by the runtime identities and
   deployers. Never copied to a workstation (unchanged).
2. **Non-secret owner config** (`terraform.tfvars`, `backend.hcl`): objects under `config/` in the Terraform state
   bucket (`gs://<project>-tfstate/config/`), versioned with the bucket. `scripts/setup.sh infra` pulls them and
   `scripts/setup.sh infra-push` stores an edit (task 112). Its readers are the state's readers, who can already
   read every production secret, so it adds no reader.
3. **Workstation secrets** (none today): if a tool on a workstation ever needs a real secret, it gets a Secret Manager
   secret whose container and per-person IAM are in Terraform, and an entry in the committed manifest
   `infra/workstation-secrets.list` (secret name → git-ignored local file); `setup.sh infra` fetches the listed
   secrets. A value Terraform itself needs is read by Terraform from Secret Manager (a data source), not copied to
   the workstation.
4. **Local development values:** generated on each machine by `scripts/setup.sh` (task 111), never shared.
5. **CI-only values:** GitHub repository secrets (`DEMO_EMAIL`, unchanged).

Access to classes 1–3 starts from a personal Google login with 2-step verification. Agents never fetch class 2 or 3
(the setup script and the guard refuse it in agent sessions). A person who loses access after reading the state means
rotating class 1 (`terraform apply -replace` on the generated values; runbook in `infra/README.md`).

Onboarding: a developer gets repository access and runs `bash scripts/setup.sh`; nothing secret. A GCP admin is added
only after the state bucket's IAM is managed by Terraform (a task of its own), then runs `scripts/setup.sh infra`.

## Alternatives considered
- **Secret Manager for the owner config too:** per-person IAM and auditable reads, about US$0.06 a month per secret,
  but every new version emails a "Security config changed" alert (task 092) and Terraform needs the tfvars before it
  can create anything. Kept for real secrets (class 3).
- **Password manager** (Bitwarden free, 1Password about US$3–5 a user a month): a second system and login on every
  machine, outside GCP's IAM and alerts; whoever needs the config needs a gcloud login anyway.
- **SOPS/age (or Cloud KMS) encrypted file in the repo:** the repository is public, so the ciphertext is public
  forever; an age key must itself be moved to each machine; removing a person doesn't remove history.
- **GitHub Codespaces secrets:** Codespaces only; no help on another Mac, Cloud Shell or claude.ai/code.
- **Copying by hand:** no history, no revocation, and the next machine has the same problem.

## Consequences
- **Good:** no new GCP resource and about US$0 a month today; history through the bucket's versioning; one place per
  class; a workstation never holds production secrets; a developer's onboarding needs nothing secret.
- **Bad / trade-offs:** nobody's read of the config or the state is recorded (Data Access logs off, SEC-32; not
  turned on now). The state bucket's IAM was set by hand, outside Terraform, until the follow-up below. Whoever can
  read the config can read every production secret in the state.
- **Follow-ups:** task 111 (workspace setup), task 112 (owner config and workstation secrets). Before a second GCP
  admin: the state bucket's IAM and the admin's project roles in Terraform (task to draft then). Data Access logs for
  Cloud Storage and Secret Manager when a second admin joins (SEC-32).
