# Full security review – 2026-11-08

- **Commit:** `main` at 76d6e83 (after tasks 069 and 076).
- **How:** five read-only reviewers in parallel, one per area: auth and sessions (AUTH), data access and RLS (ACC), web surface and files (WEB), GCP and CI/CD (INF), supply chain, secrets and tooling (SUP). Nothing was changed in the repo, GitHub or GCP. No e2e runs.

## Findings by gap

### SEC-01, SEC-02, SEC-05 · P0 · details held back
The repo is public, so the evidence and attack paths for open P0 gaps are added here when each is fixed (`docs/SECURITY.md`, "Disclosure"). SEC-01 and SEC-05: task 078 (PR #56). SEC-02: an owner setting.

### SEC-03 · Medium · CONFIRMED · fixed (PR #55, task 079) – open redirect through `safeNext` (AUTH-1)
- `packages/auth/src/redirect.ts:27-31` rejects only `//` and `/\`. Browsers strip tab, CR and LF before parsing, so `safeNext("/\t/evil.example")` is returned unchanged and `new URL(it, base)` is `https://evil.example/`. Used by `apps/shell/features/auth/login-form.tsx:29` and `signup-form.tsx:30` via `window.location.assign`.
- **Attack:** `https://<app>/login?next=/%09/evil.example/login` – the victim signs in on the real site and lands on a look-alike asking for the password again.
- **Fix:** resolve and compare origins (`new URL(next, "http://x").origin === "http://x"`, return path + search + hash), or reject `[\x00-\x1f\x7f\\]`; add tab, newline and `%09` cases (and a property test) to `redirect.test.ts`.

### SEC-04 · Medium · CONFIRMED · fixed (PR #54, task 080) – `reset:local` can reach production (SUP-4)
- `apps/dashboard/features/demo/local-reset.ts:9-40` accepts host localhost/127.0.0.1/::1 and database `app` or `app_lane<n>`. Production's database is also `app` (`infra/scripts/environment.sh:9`), and the deploy reaches it at `127.0.0.1:5432/app` through `cloud-sql-proxy`. The comment claiming tunnels are refused is wrong for production.
- **Fix:** refuse when the server looks like Cloud SQL (a `cloudsqlsuperuser` role or `cloudsql.*` settings), or require a marker only local databases have; add a test.

### SEC-06 · Medium · CONFIRMED – `main` runtime is the database owner (INF-3, ACC-1)
- `infra/scripts/environment.sh:41` (`DB_LOGIN="$MAIN_OWNER_LOGIN"`), `packages/db/src/pool-config.ts` (`-c role=app_user`). Live: the three main zones run as `app` with `db-password`. `app` owns every object and is in `cloudsqlsuperuser`.
- Any SQL-execution foothold can `RESET ROLE` on a pooled connection and read every workspace. Previews already use the SET-only `preview_runtime`.
- **Fix:** task 074 – a `main_runtime` login (NOINHERIT, SET-only member of `app_user`, connection limit) with its own secret; runtime accounts read only that secret; no DB secret for example-zone if it doesn't need one; the deploy's runtime check asserts `SET ROLE app` fails.

### SEC-07 · Medium · CONFIRMED – unbounded uploads, no cleanup (WEB-1)
- `packages/storage/src/index.ts:20-33` signs a 15-minute PUT URL with no length range; `apps/dashboard/features/attachments/actions.ts:39-91` (start) and `:97-145` (finish); `infra/storage.tf:19-36` has no lifecycle rule on the main bucket.
- **Impact:** a signed-in user can store far more than the declared size, and unconfirmed or orphaned uploads are never removed (unbounded storage cost).
- **Fix:** sign `x-goog-content-length-range: 0,<max>`; a cleanup job for rows unconfirmed after an hour and their objects; a sweep for objects without a row; optionally a per-workspace upload limit.

### SEC-08 · Medium · CONFIRMED – files outlive their workspace (WEB-2)
- `apps/dashboard/features/workspaces/settings-actions.ts:58-85` deletes the workspace; the `attachment` rows cascade (`packages/db/src/schema.ts:311+`) but no code removes the objects.
- **Fix:** delete the `<workspaceId>/` prefix after commit (object keys start with it), or queue it; a periodic sweep for prefixes whose workspace is gone.

### SEC-09 · Medium · CONFIRMED – no email verification or reset; sign-up enumeration (AUTH-2, AUTH-4)
- `packages/auth/src/server.ts:20`: `emailAndPassword: { enabled: true, minPasswordLength: 8 }`, no `requireEmailVerification`, `sendVerificationEmail` or `sendResetPassword`.
- **Impersonation:** sign up as `ceo@client.com`, join with a leaked invite link; admins see a trusted address. **Squatting:** register someone's address first; they're locked out with no reset. This also applies to `DEMO_EMAIL` (demo data only).
- **Enumeration:** sign-up answers 422 `USER_ALREADY_EXISTS…` (`better-auth/dist/api/routes/sign-up.mjs:155,204`) and the form shows it. Sign-in is fine (generic error, dummy hash on a miss).
- **Fix:** an email provider, `requireEmailVerification: true` (which also makes the duplicate answer generic) and a reset flow; or an ADR accepting it for the POC.

### SEC-10 · Medium · PLAUSIBLE – rate limiting is per instance; no lockout (AUTH-3)
- `packages/auth/src/server.ts:21` keeps Better Auth's memory store: 3 per 10 s per IP per path, per instance (main `max_instances` 5). No lockout, 8-character minimum, no breached-password check.
- Better Auth uses `x-forwarded-for` only when it has a single value; anything else goes into one shared `no-trusted-ip|<path>` bucket. A spoofed XFF therefore doesn't give fresh buckets, but a multi-hop XFF from a future load balancer would put everyone in one bucket (a sign-in DoS). Task 068 found no "could not determine a client IP" warnings on the first preview, so Cloud Run sends a single value today.
- **Fix:** set `advanced.ipAddress` explicitly; `rateLimit.storage: "database"` (or Redis); an account-level failure counter.

### SEC-11 · Medium · CONFIRMED – no dependency or secret automation (SUP-5)
- Dependabot alerts and security updates are off (API 403), no `.github/dependabot.yml`, no `pnpm audit` job, no gitleaks, no CodeQL. Secret scanning and push protection are on; non-provider patterns are off.
- Late-October criticals (Next.js GHSA-2464-fhr4-w9xw; Better Auth GHSA-965c-763c-88jm, GHSA-r4xp-prcw-77qf) are patched in the lockfile only because of a timely upgrade.
- **Fix:** Dependabot alerts and updates (npm and github-actions, grouped weekly); `pnpm audit --prod --audit-level=high` with a reviewed allowlist; a gitleaks job; non-provider secret patterns.

### SEC-12 · Medium · CONFIRMED – guard hook gaps (SUP-2, SUP-3)

### SEC-19 · Low · CONFIRMED – no security headers (WEB-3)

### SEC-20 · Low · CONFIRMED – zones reachable directly (WEB-4, INF-6)
